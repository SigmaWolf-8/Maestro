## Executive Summary

This document defines the complete document management architecture for the Maestro ERP system, integrating four major subsystems with PlenumNET's post-quantum cryptographic and timing infrastructure.

**What the system does:** Every document that enters Maestro — from any source — is automatically classified into a 13-level Work Breakdown Structure via full-document OCR, routed through a collaborative review pipeline, precision-timestamped at every lifecycle stage, signed with post-quantum TL-DSA signatures, indexed for sub-second search, and packaged into cryptographically verifiable archives at project closeout. A unified event bus makes all subsystems composable rather than siloed.

**What is live today:** 28 PlenumNET API endpoints are production-ready and callable by Maestro with no prerequisite work: 5 femtosecond timing, 4 phase encryption, 10 ternary computing, and 9 PQTI signing/encapsulation (TL-DSA signing + verification + key generation, TL-KEM encapsulation + decapsulation + key generation, CryptoInteropBridge export, health). All Maestro-side development (classification engine, review pipeline, archive assembly, offline queue, event bus) can proceed immediately with zero external blockers and full cryptographic integration from day one.

**Strategic value:** No construction ERP competitor offers automatic WBS classification, structured multi-party document review, femtosecond-precision temporal provenance, and a live post-quantum integrity chain from field capture to dispute verification years later — all within a single, event-sourced, fully searchable platform.

**Immediate next steps:** Begin CE-1 (OCR pipeline), EB-1 (event bus core), and FQ-1 (offline queue core) in parallel. See [Next Steps](#next-steps) for the full action plan.

## Repository Boundary

> **SEPARATION OF CONCERNS**
>
> Two repositories. One boundary. Clear ownership.
>
> **SigmaWolf-8/Maestro** — The ERP application. Document management, WBS logic, WBS Classification Engine, ONLYOFFICE review pipeline, archive assembly, offline queue, unified event bus, UI, business rules. Maestro is a consumer of cryptographic and timing services. It never implements, wraps, or redistributes crypto code.
>
> **SigmaWolf-8/Ternary** — PlenumNET. The post-quantum ternary computing platform. All cryptographic primitives (TL-DSA, TL-KEM, phase encryption), all timing infrastructure (HPTP femtosecond timestamps), the CryptoInteropBridge, and the forthcoming signing microservice live here. The signing microservice is a PlenumNET service that Maestro calls over HTTP — it is not a Maestro module.
>
> This boundary is non-negotiable. Cryptographic code stays in the Ternary repo where it benefits from the existing CI/CD pipelines (`build-kernel.yml`, `test-kernel.yml`, `security-scan.yml`), the formal verification framework, the side-channel analysis, and the CAVP package infrastructure. Maestro's CI/CD has no business touching crypto.

## Foundational Correction

> **ARCHITECTURAL PRINCIPLE**
>
> Version 1.0 of this document fabricated three API endpoints that do not exist: `/api/pqti/sign`, `/api/pqti/timestamp`, and `/api/pqti/bridge/export`. These paths are explicitly listed in the repository's `GITHUB-REPOSITORY-ARCHITECTURE.md` under the heading **"Endpoints That Do NOT Exist."**
>
> The PQTI layer is Rust kernel code only. It has no REST API surface. TL-DSA signing lives at `src/kernel/src/crypto/tl_dsa.rs` — a Rust library module, not an HTTP service. CryptoInteropBridge is a Rust struct at `src/kernel/src/compat/crypto_interop.rs`, not a callable endpoint.
>
> This document separates what is **available now via live API** from what **requires the Rust signing microservice** currently under parallel development.

## Decision Log

Key architectural decisions and their rationale, preserved to prevent revisiting settled debates.

| Decision | Rationale | Alternatives Considered |
|----------|-----------|------------------------|
| **Separate repositories** (Maestro vs Ternary) | Cryptographic code requires its own CI/CD, formal verification, side-channel analysis, and CAVP infrastructure. Mixing ERP business logic with crypto code creates security surface area and certification risk. | Monorepo — rejected due to CI/CD contamination risk |
| **Rust signing microservice (Axum)** over WASM or Node FFI | Preserves constant-time guarantees, side-channel analysis validity, and formal verification chain. WASM introduces garbage collection and unpredictable memory layout; FFI introduces cache behavior outside analysis scope. Now live on port 3001 with 9 endpoints — decision validated. | WASM compilation — rejected (invalidates `side_channel.rs`). Node.js FFI — rejected (same). |
| **HTTP API boundary** between Maestro and PlenumNET | Clean separation, language-agnostic, independently deployable, testable via standard HTTP tools. Kong API gateway already manages 17 services. | Direct library linking — rejected (violates repo boundary). gRPC — rejected (unnecessary complexity for current scale). |
| **Full-document OCR** over first-page sampling | Construction documents bury critical classification data deep in the document (revision tables on page 47, CSI codes in appendices). First-page sampling misses too much. | First-page OCR — rejected (insufficient accuracy). Filename-only parsing — rejected (too fragile). |
| **Deterministic WBS tagging** over suggestion-based | Manual classification queues become permanent backlogs. "Suggested" placement means "deferred" placement means "no" placement. Zero-intervention is the only model that maintains data integrity at scale. | Human-in-the-loop confirmation — rejected (creates bottleneck). |
| **13-dimensional WBS depth** | Real construction project decomposition requires granularity beyond typical 3–5 level WBS trees. Insurance claims and dispute resolution demand element-level traceability. | Flat or shallow WBS — rejected (insufficient for regulatory and legal requirements). |
| **ONLYOFFICE Document Server** (self-hosted) | Open-source, self-hosted, full collaborative editing, native track changes, no per-seat licensing for on-premise. Maestro controls the deployment. | Google Docs API — rejected (cloud dependency, data sovereignty). Collabora — viable alternative but smaller ecosystem. Microsoft 365 — rejected (licensing cost, cloud lock-in). |
| **Append-only event log** | Immutable audit trail required for construction dispute scenarios. Event sourcing enables full system state reconstruction. Dead-letter handling prevents event loss. | Mutable database records — rejected (no auditability). External message broker (Kafka) — deferred (unnecessary at current scale; can migrate later). |

### Architecture

A Rust microservice using Axum, running on port 3001 alongside the Node.js backend **in the Ternary repo / PlenumNET deployment**, calling `tl_dsa.rs` and `tl_kem.rs` directly. Proxied through the main application server. This is a PlenumNET service — it ships from SigmaWolf-8/Ternary, deploys with PlenumNET, and is governed by PlenumNET's CI/CD and security scanning pipelines. ## Unified Event Model

> **COMPOSABILITY PRINCIPLE**
>
> Every document action in Maestro — regardless of which subsystem triggers it — emits a standardized event that any Maestro module can subscribe to. All subsystems are composable stages of a unified document lifecycle, connected by a single event bus.

### The Problem Without Events

Without a unified event model, each subsystem operates in isolation. The offline queue uploads a document and stores it. The archive engine packages documents at closeout. The review pipeline processes approvals. But none of them know what the others are doing. An invoice uploaded via the offline queue doesn't notify the accounting module. A submittal that completes review doesn't trigger RFI tracking updates. Integration becomes point-to-point wiring — brittle, expensive, and invisible.

### Event Schema

Every document event conforms to a single schema carrying full context for any subscriber to act without querying back to the source.

| Field | Type | Description |
|-------|------|-------------|
| `eventId` | UUID | Unique event identifier for deduplication and audit trail |
| `eventType` | Enum | `document.captured`, `document.classified`, `document.uploaded`, `document.reviewed`, `document.approved`, `document.version_locked`, `document.archived`, `document.signed`, `document.shared` |
| `timestamp` | HPTP Object | Femtosecond-precision timestamp from PlenumNET (with device fallback fields for offline scenarios) |
| `documentId` | UUID | Maestro's internal document identifier |
| `wbsCode` | String | Full WBS path (up to 13 dimensional levels) as assigned by the Classification Engine |
| `documentType` | Enum | Classification Engine's type determination: `submittal`, `rfi`, `invoice`, `inspection_report`, `change_order`, `shop_drawing`, etc. |
| `userId` | UUID | User who triggered the action |
| `sha3Hash` | String | SHA-3 hash of the document at the time of this event |
| `source` | Enum | Intake path: `field_capture`, `bulk_import`, `email_ingestion`, `api_upload`, `manual_upload`, `onlyoffice_review` |
| `metadata` | Object | Event-type-specific payload (varies per eventType) |
| `tldsaSignature` | Object \| null | TL-DSA signature from the live PQTI microservice. Null only in zero-connectivity offline scenarios where the signing call is deferred. |

### Event Types and Subscribers

| Event Type | Emitted By | Example Subscribers |
|------------|-----------|---------------------|
| `document.captured` | Offline Field Queue (at field capture) | Audit log, queue status dashboard |
| `document.classified` | WBS Classification Engine (at intake) | WBS tree UI refresh, project completeness tracker |
| `document.uploaded` | Offline Field Queue — Background Sync (on server receipt) | Accounting module (if invoice), RFI tracker (if submittal), safety dashboard (if inspection) |
| `document.staged` | ONLYOFFICE Review Pipeline (registered for review) | Review assignment engine, reviewer notification system |
| `document.reviewed` | ONLYOFFICE Review Pipeline (markup complete) | Approval workflow, revision tracker |
| `document.approved` | ONLYOFFICE Review Pipeline (approved by reviewer) | Version lock trigger, notification to submitting party |
| `document.version_locked` | ONLYOFFICE Review Pipeline (final version sealed) | Archive readiness tracker, compliance checklist |
| `document.archived` | Archive Assembly Engine (at project closeout) | Legal hold system, records retention scheduler |
| `document.signed` | PQTI microservice integration (TL-DSA signature applied) | Integrity dashboard, compliance audit log |
| `document.shared` | Phase encryption export (sent to external party) | Distribution log, external party tracker |

### Implementation Architecture

The event bus is an in-process publish/subscribe system within the Maestro Node.js backend. Events are persisted to an append-only event log before dispatch, guaranteeing that no event is lost even if a subscriber is temporarily unavailable. Subscribers register declaratively.

The event log doubles as a complete audit trail satisfying requirements for records retention, eDiscovery, and regulatory compliance (see [Compliance](#compliance-and-auditability)). Every document action in the system's history is reconstructible from the event log alone.

### Event Bus — Implementation Phases

| Phase | Repo | Description | Effort | Dependencies |
|-------|------|-------------|--------|-------------|
| **EB-1** | Maestro | Event schema definition, event bus core (publish/subscribe), append-only event log with persistence | 2–3 weeks | None |
| **EB-2** | Maestro | Event emission integration: wire all document actions across all subsystems to emit standardized events | 2–3 weeks | EB-1 + at least one subsystem phase complete |
| **EB-3** | Maestro | Subscriber framework: declarative registration, dead-letter handling, replay capability for new subscribers | 2–3 weeks | EB-1 |
| **EB-4** | Maestro | Cross-module subscribers: accounting on invoice, RFI on submittal, safety on inspection, compliance audit log | 3–4 weeks | EB-2 + EB-3 |

**✅ All Event Bus phases are pure Maestro repo work.** No PlenumNET dependency.

## WBS Classification Engine — Intelligent Intake Pipeline

> **ARCHITECTURAL MANDATE**
>
> Every document that enters Maestro through any path — field capture, bulk import, email ingestion, subcontractor ZIP, legacy migration, API upload, ONLYOFFICE review completion — passes through the WBS Classification Engine before any other processing occurs. Classification is not optional. It is not suggested. It is automatic, silent, and 100% accurate. No document reaches the WBS tree, the timing layer, the signing layer, the review pipeline, or the archive engine without a machine-assigned WBS code.
>
> The WBS tree supports up to **13 dimensional levels** of hierarchical depth. The Classification Engine resolves to the deepest applicable node across all 13 levels — not to a convenient intermediate level. A document that belongs at Level 11 gets tagged at Level 11.
>
> This is pure Maestro repo development. No PlenumNET dependency. The Classification Engine is upstream of everything.

### The Problem

Construction document management systems assume documents arrive with context. A field worker photographs a rebar inspection from inside the correct WBS node. A project coordinator uploads a submittal into the right folder. The system works when the user provides the context. It fails in every other scenario.

Subcontractors email 200 invoices in a flat ZIP. An engineer dumps a folder of shop drawings with filenames like `SD-FR-2026-0134-R2.pdf`. A firm migrates 50,000 legacy records from a defunct platform. In all of these cases, the documents arrive with no WBS context, incomplete metadata, or organizational schemes that don't map to the project's Work Breakdown Structure.

The industry response is a manual sorting inbox. Documents pile up. Classification is deferred. Deferred classification becomes no classification. Unclassified documents become invisible to queries, absent from archives, and missing from compliance reports. This is a data integrity failure that compounds over project duration.

### Stage 1 — Document Ingestion and Full OCR

The engine accepts documents from all intake paths through a unified ingestion interface. Full OCR is performed on every page. For natively digital documents (born-digital PDFs, Word files, spreadsheets), text is extracted directly from the document structure. For scanned documents, photographs, and image-based PDFs, OCR produces a complete text layer. The output is a structured text corpus representing the entire document content, page by page.

OCR processing is parallelized across pages. A 200-page specification book does not wait for sequential page processing. The engine distributes pages across available workers and assembles the complete text corpus when all pages are resolved. On completion, the engine emits a `document.classified` event via the Unified Event Bus.

### Stage 2 — Entity Extraction and Feature Identification

| Feature Category | What the Engine Extracts |
|-----------------|------------------------|
| Title Block Data | Drawing numbers, revision codes, sheet numbers, project identifiers, discipline codes, dates, approval stamps, engineer-of-record names |
| CSI MasterFormat Codes | Division numbers (01–49), section numbers, and specification references found anywhere in document body, headers, or footers |
| Document Type Signatures | Structural patterns identifying submittals, RFIs, change orders, invoices, inspection reports, test results, meeting minutes, correspondence, permits, certificates |
| Organizational References | Company names matched against project directory, subcontractor identification, trade classification |
| Spatial References | Building identifiers, floor/level numbers, grid line references, room numbers, zone designations, area codes |
| Temporal Markers | Dates, revision histories, schedule references, milestone markers, phase identifiers |
| Regulatory References | Code citations, permit numbers, inspection authority references, compliance standard identifiers |
| Structural Metadata | Page counts, document dimensions, file format characteristics, embedded metadata fields, EXIF data from photographs |

### Stage 3 — 13-Dimensional WBS Resolution

Extracted features are matched against the project's WBS tree using a multi-signal scoring algorithm. The engine computes a weighted confidence score across all features, resolving to the WBS node with the highest aggregate match. Resolution operates across **up to 13 dimensional levels** of WBS hierarchy — the engine does not stop at a convenient intermediate level. A document that belongs at Level 11 of 13 (e.g., `Project/03-Concrete/Cast-in-Place/Foundations/Pile-Caps/Building-C/Grid-F7/Inspection-Reports/Rebar/Pre-Pour/Cycle-2/Field-Verified`) gets tagged at Level 11, not at Level 3.

The 13-level depth accommodates the full complexity of real construction project decomposition: project → discipline → subdivision → system → building → zone → element → activity type → document class → trade → inspection cycle → verification stage → record type. Each level narrows the classification, and the engine traverses all 13 levels to find the deepest matching node with sufficient confidence.

Resolution rules are project-specific and configurable. Each project's WBS tree carries a classification ruleset initialized from CSI MasterFormat division mappings and refined automatically as documents accumulate (see Stage 5).

### Stage 4 — Deterministic Tagging

The engine assigns the resolved WBS code to the document. This assignment is deterministic — not suggested, not queued for review, not flagged for human confirmation. The document receives its WBS code and proceeds immediately to the next lifecycle stage (HPTP timestamping, SHA-3 hashing, event emission, queue entry or direct storage).

Below-threshold classifications escalate to a secondary analysis pass with expanded feature weighting before making a final determination. The design target is zero-intervention classification.

### Stage 5 — Continuous Feedback Loop

Every document that enters the system through any path — including documents classified by field workers who already know the WBS context — feeds the classification model. Manual reclassifications are treated as high-weight corrections. The feedback loop is passive. No user ever interacts with "training" or "classification settings." The engine learns from normal document flow.

### Full-Text Search Index

Every word extracted from every page of every document is written to a full-text search index at the moment of classification. This index is the project's searchable memory.

| Index Field | Content |
|-------------|---------|
| Full text corpus | Every word from every page, preserving page-level position for snippet generation |
| WBS path | The assigned WBS code (up to 13 levels), enabling scoped queries at any depth ("search only within 03-Concrete" or "search within 03-Concrete/Foundations/Pile-Caps/Building-C") |
| Extracted entities | All features from Stage 2 as structured, filterable facets |
| Document metadata | File type, page count, upload source, user identity, HPTP timestamp, SHA-3 hash |

## ONLYOFFICE Document Review Pipeline

> **WORKFLOW ACCELERATOR**
>
> ONLYOFFICE is not just an editing tool. It is a document review pipeline. Bulk upload → auto-register with document server → assign reviewers per WBS node → collaborative markup → approval → version lock. Every stage emits events via the Unified Event Bus. Every document is classified by the WBS Classification Engine. Every action is HPTP-timestamped.

### The Problem

Construction projects require multi-party document review. Shop drawings need engineer approval. Submittals need architect review. Specifications need owner sign-off. Change orders need cost verification from multiple stakeholders. Today, this review process happens outside the document management system — via email attachments, printed markups, disconnected PDF annotation tools, or verbal approvals with no audit trail.

The result: no single source of truth for review status, no verifiable record of who approved what and when, no traceability from markup to final version, and no integration between the review process and the document's lifecycle in the WBS.

### ONLYOFFICE Document Server — Deployment Notes

ONLYOFFICE Document Server is deployed self-hosted within Maestro's infrastructure under the AGPLv3 open-source license (no per-seat fees for on-premise deployment). Key operational parameters: supports concurrent collaborative editing sessions limited by server resources (recommend 4+ CPU cores, 8+ GB RAM for 50+ simultaneous reviewers); document format support includes DOCX, XLSX, PPTX, and PDF with conversion; very large CAD files (DWG/DXF) are handled via PDF conversion prior to review staging. Failover: ONLYOFFICE sessions are stateless on the client side — if the Document Server restarts, reviewers reload the document and resume. Document state is persisted to Maestro's storage layer, not to the Document Server.

### Stage 1 — Bulk Upload and Auto-Registration

Documents arriving through any intake path are first classified by the WBS Classification Engine, then automatically registered with the ONLYOFFICE Document Server. Registration creates an editing session for each document without user action. For bulk imports — a subcontractor submitting 50 shop drawings in a ZIP — every document is classified, registered, and ready for review within seconds. Each registration emits a `document.staged` event.

### Stage 2 — WBS-Based Reviewer Assignment

Each WBS node carries a reviewer configuration: which roles or named individuals are responsible for reviewing documents in that node. When a document is classified and registered, Maestro's assignment engine reads the WBS node's reviewer configuration and assigns reviewers.

Reviewer assignment is hierarchical across all 13 WBS levels. A reviewer assigned to WBS node `03-Concrete` (Level 2) automatically reviews documents in all child nodes down to Level 13 unless a deeper node has its own explicit assignment. Review policies propagate down the WBS tree without per-document configuration.

Assignment notifications are emitted as events. Subscribing modules (email, in-app alerts, Slack, mobile push) notify reviewers through their preferred channel.

### Stage 3 — Collaborative Markup

Reviewers open the document in ONLYOFFICE's collaborative editor directly within Maestro's interface. Multiple reviewers can work simultaneously. All changes are tracked via ONLYOFFICE's native track-changes and commenting features.

Every edit session is HPTP-timestamped at session start and session end. Configurable review windows per WBS node; overdue reviews trigger escalation events.

### Stage 4 — Approval Workflow

Reviewers submit decisions: **approved**, **approved with comments**, **revise and resubmit**, or **rejected**. Each decision is a `document.reviewed` event with reviewer identity, decision, HPTP timestamp, and comments.

For documents requiring multiple approvals, Maestro tracks per-reviewer status. The document advances to version lock only when all required approvals are satisfied. "Revise and resubmit" routes the document back with markup attached, creating a new revision cycle with full traceability.

### Stage 5 — Version Lock

When all approvals are received, Maestro locks the document version — no further edits without creating a new revision. Version lock emits `document.version_locked`.

At lock: the document is re-processed through the WBS Classification Engine (in case markup changed classification-relevant content), re-hashed with SHA-3, HPTP-timestamped, and signed with TL-DSA via the live PQTI microservice (`/api/pqti/tldsa/sign`). The locked version is what enters the archive — only approved content, not draft markup.

### ONLYOFFICE Pipeline — Integration Map

| Integration Point | Behavior |
|------------------|----------|
| WBS Classification Engine | Documents classified before review entry. WBS code determines reviewer assignment. Post-review re-classification if content changed. |
| Unified Event Bus | Every stage emits events: `document.staged`, `document.reviewed`, `document.approved`, `document.version_locked`. |
| HPTP Timing | Session start/end, each decision, and version lock are HPTP-timestamped. |
| Offline Field Queue | Field-captured documents auto-staged for review upon server receipt and classification. |
| Archive Assembly Engine | Only version-locked documents enter archives. Manifest includes full review history. |
| TL-DSA Signing | Version-locked documents receive TL-DSA signatures via the live PQTI microservice. Integrity chain extends from capture through approval to archive. |
| Full-Text Search Index | Review status indexed. "All submittals awaiting engineer approval" returns sub-second results. |

## Automated Archive Export

### The Problem

Construction projects generate thousands of documents over months or years. At closeout, the general contractor must retain records for 7–10+ years. Today, archival is manual, unverifiable, and carries no proof of completeness, integrity, or temporal provenance. In disputes, the inability to prove document provenance is a material legal vulnerability.

### Archive Assembly Engine

**1. WBS Tree Walk.** Maestro traverses the project's Work Breakdown Structure across all 13 dimensional levels. Every WBS node containing documents becomes a directory in the archive, preserving the full hierarchical depth. Because every document was classified by the WBS Classification Engine at intake, the tree walk produces a complete archive with zero orphaned documents.

**2. Document Collection.** For each WBS node, Maestro collects every version and revision. Only version-locked documents (those that completed the ONLYOFFICE review pipeline) are primary records. Drafts and in-review versions go to a separate `/drafts/` directory.

**3. Manifest Generation.** Structured manifest (JSON + human-readable PDF): filename, WBS path, document type, version history, upload user, file size, SHA-3 hash, classification confidence score, review history (reviewers, decisions, timestamps), version lock timestamp.

**4. Package Assembly.** All documents, manifest, search index, and event log assembled into a compressed archive. `archive.sealed` event emitted via Unified Event Bus.

### PlenumNET Integration

**Today:** HPTP femtosecond timestamp at archive seal. Phase encryption for sensitive documents. Per-document TL-DSA signing via `/api/pqti/tldsa/sign`, manifest signing at TL-DSA-87, and CryptoInteropBridge export via `/api/pqti/tldsa/export` for external verification. TL-KEM key encapsulation via `/api/pqti/tlkem/encapsulate` for encrypted document sharing with external parties.

## Offline Field Upload Queue

### The Problem

Construction sites have unreliable connectivity. If the system requires a network connection to accept a document, workers forget to upload later or work around the system entirely. Compliance-critical documentation — rebar placement before concrete pour, fire-stopping inspection, structural connection verification — gets lost. This is a legal exposure and data integrity problem.

### Queue Architecture

**1. File Capture.** Field worker photographs or selects a document through Maestro's mobile/web interface. The application knows the WBS context.

**2. Local Queue Entry.** File written to IndexedDB with metadata: file binary, WBS destination path, user identity, status flag, integrity data.

**3. Background Sync.** Service Worker monitors connectivity. Uploads processed sequentially on reconnect. Failed uploads re-queue with incremental backoff. Each upload emits `document.uploaded`.

**4. Server Receipt, Classification, and Routing.** The WBS Classification Engine processes the document through full OCR, assigns a 13-level WBS code, cross-validates against the field worker's capture context (engine overrides if mismatched, discrepancy logged). Document indexed in full-text search. If the WBS node has a reviewer configuration, the document auto-stages in the ONLYOFFICE pipeline. `document.classified` event fires.

**5. Progress Visibility.** Persistent status indicator: pending, uploaded, classified, staged for review, failures.

### Offline Edge Cases

**Large files and partial uploads:** The Service Worker uses chunked upload with resumption. If an upload is interrupted mid-transfer, the next sync attempt resumes from the last successful chunk rather than restarting. SHA-3 integrity verification on the server confirms completeness.

**Conflict resolution:** Documents captured offline are append-only — they are new records entering the system, not edits to existing records. If two workers photograph the same physical artifact (e.g., the same rebar section), both photos enter the WBS as separate documents with their own HPTP timestamps, and the Classification Engine tags both to the same WBS node. Duplicate detection is a downstream concern handled by the search index (flagging documents with identical or near-identical content in the same WBS node), not a queue-level problem.

### Timing and Signing at Capture

**HPTP Timing (live today):**

**Degraded connectivity** (common) — enough signal for a lightweight GET request but not for a multi-megabyte upload. The HPTP timestamp succeeds; the file queues.

**Zero connectivity** (less common) — HPTP call queued alongside file. Device clock provides interim timestamp. On reconnect, both timestamps recorded: `captured_device_time`, `hptp_attested_time`, `delta_ms`.

**TL-DSA Signing (live today):** SHA-3 hash computed locally at capture. TL-DSA signature obtained from `/api/pqti/tldsa/sign` — same connectivity logic as timing (succeeds on degraded connectivity, queues on zero connectivity). Server verifies signature via `/api/pqti/tldsa/verify` before accepting document into Classification Engine pipeline.
