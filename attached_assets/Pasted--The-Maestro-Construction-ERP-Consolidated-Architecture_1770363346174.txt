## 1. Strategic Architecture Overview

The Maestro is a multi-tenant, all-industry ERP web application with a split frontend/backend architecture. It replaces legacy tools (including MS Access-based reporting) with AI-native analytics, in-browser Office document editing, and post-quantum security via the PlenumNET/SFK infrastructure.

## 2. Technology Stack & Key Decisions

### Core Stack

| Layer | Technology | Rationale |
|-------|-----------|-----------|
| **Frontend** | React 18 + Vite | Fast HMR, tree-shaking, TypeScript-first |
| **UI Components** | shadcn/ui + Tailwind CSS | Composable, themeable, accessible |
| **Client State** | TanStack Query v5 (server), Zustand (UI) | Selector-based subscriptions, no context re-render storms |
| **Routing** | wouter | Lightweight, hook-based |
| **Forms** | react-hook-form + Zod | Type-safe validation, minimal re-renders |
| **Backend** | Express.js + TypeScript (strict) | Mature, well-understood, extensible |
| **ORM** | Drizzle ORM | Type-safe SQL, zero runtime overhead, migration system |
| **Database** | PostgreSQL (Replit-native) | Proven, extensible, RLS, ltree, JSONB |
| **Auth** | Azure AD (production) / Replit OIDC (dev) | Single federated IdP, JWT-based |
| **Gateway** | Kong Konnect | Plugin architecture for PlenumNET security |
| **AI** | LangChain + OpenAI/Ollama (RAG pipeline) | Natural language → SQL → narrative |
| **O365** | Microsoft Graph API + WOPI | In-browser editing, email, calendar |
| **Real-time** | Server-Sent Events (SSE) | One-way push, auto-reconnect, Kong-compatible |

### Key Architectural Decision: PostgreSQL-Native, Supabase-Deferred

**Decision:** Use Replit's built-in PostgreSQL directly with Drizzle ORM. Defer Supabase migration to post-MVP stabilization.

**Rationale:**

- Supabase IS PostgreSQL — migration is a `pg_dump` → `pg_restore` with zero code changes.
- Drizzle ORM schemas, migrations, and queries work identically on both.
- Row-Level Security policies written now transfer directly.
- Eliminates an external dependency during rapid development.
- The `DATABASE_URL` environment variable pattern ensures the switch is a config change, not a code change.

**Migration Trigger Criteria (for future evaluation):**

- Schema is stable (no weekly migration churn)
- RLS policies are tested and production-proven
- Seed data and test fixtures are finalized
- Team needs managed hosting, built-in Realtime, or Supabase Studio tooling

**Supabase Feature Mapping (for when migration occurs):**

| Supabase Feature | Current Equivalent | Migration Effort |
|---|---|---|
| Auth (Azure AD) | JWT + Azure AD OAuth2 flow | Low — swap auth provider config |
| Realtime subscriptions | SSE from Express server | Low — swap client listener |
| Row-Level Security | Same Postgres RLS policies | **Zero** — identical SQL |
| Dashboard/Studio | Drizzle Studio / pgAdmin | Cosmetic |
| Edge Functions | Express API routes | Medium — optional, no requirement |
| Storage (S3-backed) | OneDrive via Graph API | N/A — different strategy |

## 3. Database Architecture (PostgreSQL-Native)

### Schema Overview (Consolidated)

The schema is optimized from the original 18-table design down to a streamlined set with JSONB for flexible metadata, ltree for hierarchical WBS, and partitioned audit logging.

```sql
-- Core Extensions Required
CREATE EXTENSION IF NOT EXISTS "ltree";
CREATE EXTENSION IF NOT EXISTS "pgcrypto";
CREATE EXTENSION IF NOT EXISTS "pg_trgm";  -- For fuzzy text search
```

### Table Summary

| Table | Purpose | Key Features |
|-------|---------|-------------|
| `tenants` | Multi-tenant root | Branding JSONB, subscription tier |
| `users` | User accounts | Azure AD identity mapping |
| `tenant_memberships` | User↔Tenant link | Role enum, permissions JSONB override, group_ids array |
| `user_groups` | Named permission groups | Per-tenant, JSONB permissions |
| `projects` | Construction projects | Budget, schedule, status, currency |
| `wbs_nodes` | Work Breakdown Structure | **ltree path**, cost tracking, schedule |
| `wbs_master_codes` | WBS template library | Industry-standard code definitions |
| `documents` | Document registry | **meta JSONB** (replaces document_meta_tags), OneDrive refs |
| `customers` | Client/customer CRM | Contact info, billing |
| `vendors` | Supplier management | Contact info, categories |
| `vendor_contacts` | Vendor contact people | Per-vendor contacts |
| `quotes` | Quotations | Line items, status workflow |
| `navigation_items` | Dynamic menu config | Per-tenant customizable navigation |
| `notifications` | Multi-channel notifications | In-app, email, push |
| `audit_log` | Immutable audit trail | **Partitioned by month**, JSONB changes |
| `ai_report_audit_log` | AI query audit | Prompt, generated SQL, security mode |
| `ms_graph_tokens` | O365 token cache | Per-user, encrypted refresh tokens |
| `sessions` | Auth sessions (dev/compat) | JWT makes this optional in production |

### Row-Level Security Pattern

```sql
-- Enable RLS on all tenant-scoped tables
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON projects
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);

-- Express middleware sets context per request:
-- SET app.current_tenant_id = '<tenant-uuid>';
```

### WBS Engine (ltree)

```sql
CREATE TABLE wbs_nodes (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id uuid NOT NULL REFERENCES tenants(id),
  project_id uuid NOT NULL REFERENCES projects(id),
  parent_id uuid REFERENCES wbs_nodes(id),
  path ltree NOT NULL,              -- e.g., '1.2.3.4'
  code text NOT NULL,               -- Display code: '03.02.01'
  title text NOT NULL,
  level smallint GENERATED ALWAYS AS (nlevel(path)) STORED,
  budgeted_cost numeric(15,2) DEFAULT 0,
  actual_cost numeric(15,2) DEFAULT 0,
  planned_start date,
  planned_end date,
  actual_start date,
  actual_end date,
  percent_complete numeric(5,2) DEFAULT 0,
  template_code_id uuid REFERENCES wbs_master_codes(id),
  meta jsonb DEFAULT '{}',
  sort_order integer DEFAULT 0,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz DEFAULT now()
);

CREATE INDEX idx_wbs_path ON wbs_nodes USING GIST (path);
CREATE INDEX idx_wbs_project ON wbs_nodes (project_id, path);
```

### Audit Log (Partitioned)

```sql
CREATE TABLE audit_log (
  id bigserial,
  tenant_id uuid NOT NULL,
  user_id uuid NOT NULL,
  action text NOT NULL,
  entity_type text NOT NULL,
  entity_id uuid NOT NULL,
  changes jsonb,
  ip_address inet,
  user_agent text,
  created_at timestamptz DEFAULT now()
) PARTITION BY RANGE (created_at);

-- Monthly partitions (created by migration or cron)
CREATE TABLE audit_log_2026_02 PARTITION OF audit_log
  FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

## 4. AI-Powered Reporting Engine

### Overview

Replaces MS Access-based reporting with a **Retrieval-Augmented Generation (RAG)** pipeline. Users ask questions in natural language; the system generates SQL, executes it, and produces narratives, charts, and recommendations.

### Architecture

```
User Query ("Show me cost overruns for Q1")
    │
    ▼
┌──────────────────────────┐
│  AI Report Service        │
│  (ai-report-service.ts)  │
│                          │
│  1. Validate query       │
│  2. Audit log (pending)  │
│  3. NL → SQL (LangChain) │
│  4. Execute SQL          │
│  5. Results → Narrative  │
│  6. Results → Charts     │
│  7. Security enforcement │
│  8. Audit log (complete) │
└──────────────────────────┘
    │
    ▼
┌──────────────────────────┐
│  Response                │
│  • Executive summary     │
│  • Key findings          │
│  • Visualizations        │
│  • Recommendations       │
│  • XRPL witness (Mode φ)│
└──────────────────────────┘
```

### Security Modes for AI Queries

| Mode | Behavior | Use Case |
|------|----------|----------|
| **Mode φ (phi)** | Query + results witnessed to XRPL, femtosecond timestamps | Financial audits, regulatory |
| **Mode 1** | Strong post-quantum encryption, nanosecond timestamps | Enterprise daily use |
| **Mode 0** | Standard encryption, microsecond timestamps | Legacy/compatibility |

### ⚠️ Refactor Note: Supabase → Drizzle ORM

The Task 1.1 code as originally written imports `SupabaseClient` and references `this.supabase.from('ai_report_audit_log')`. Per the **PostgreSQL-Native** decision (Section 2), these must be refactored before integration:

| Original (Supabase) | Replacement (Drizzle ORM) |
|---|---|
| `import { SupabaseClient } from '@supabase/supabase-js'` | `import { db } from '../db'` |
| `this.supabase.from('audit_log').insert({...})` | `await db.insert(auditLog).values({...})` |
| `config.supabase: SupabaseClient` | `config.db: DrizzleInstance` |
| `process.env.SUPABASE_URL` | `process.env.DATABASE_URL` (already PostgreSQL) |

The Replit AI Agent should apply this refactor when integrating the service into the Express app. The business logic, types, mock data, and security mode handling remain unchanged.

### Current Capabilities (Mock Mode)

The Task 1.1 implementation provides:

- Full TypeScript type safety across client/server boundary
- Mock data for all common construction query patterns (cost overruns, schedule, vendors)
- Security mode handling with XRPL witnessing placeholders
- Comprehensive error handling with typed error codes
- Audit logging framework
- Health check and tenant usage statistics endpoints
- Zod-validated API endpoints

### Key Design Note — SQL Safety

The AI service generates SQL from natural language. Safety rails:

1. **Input validation** — harmful patterns (DROP, DELETE, INSERT, UPDATE) rejected at prompt level
2. **Tenant scoping** — all generated SQL includes `WHERE tenant_id = ?` (enforced by service, backed by RLS)
3. **Read-only execution** — AI queries execute through a read-only database role
4. **Audit trail** — every query logged with prompt, generated SQL, execution time, security mode
5. **Query timeout** — 30-second default, configurable per tenant

### WOPI Document Editing Flow

```
1. User clicks "Edit in Word" on a document
2. Frontend requests WOPI action URL from backend
3. Backend generates signed WOPI access token
4. Frontend opens Office Online iframe with WOPI URL
5. Office Online (Microsoft servers) calls YOUR WOPI endpoints:
   - GET  /wopi/files/:id           → CheckFileInfo (metadata)
   - GET  /wopi/files/:id/contents  → GetFile (bytes)
   - POST /wopi/files/:id/contents  → PutFile (save)
   - POST /wopi/files/:id           → Lock/Unlock
6. Your WOPI host proxies to OneDrive via Graph API
7. Kong gateway enforces auth + PlenumNET encryption on all WOPI traffic
```

## 6. Kong Konnect Gateway

### Plugin Architecture

All security concerns live in Kong plugins, not in Express application code. The Express backend is a pure business logic server.

| Concern | Plugin Type | Notes |
|---------|-------------|-------|
| JWT verification | Built-in (jwt) | Validates tokens, injects claims |
| Rate limiting | Built-in (rate-limiting) | Per-tenant, configurable tiers |
| CORS | Built-in (cors) | Allowed origins per environment |
| Request logging | Built-in (file-log) | Structured JSON logs |
| Phase-rotation encryption | **Custom** (Lua/Go) | PlenumNET Mode φ/1/0 |
| Ternary compression | **Custom** (Lua/Go) | Bijective ternary encoding |
| Femtosecond timestamping | **Custom** (Lua/Go) | HPTP-based timing headers |

### Service Definitions

```yaml
# kong/kong.yml (decK declarative format)

services:
```

## 7. PlenumNET Security Integration

### How PlenumNET Maps to ERP Operations

| ERP Operation | Security Mode | PlenumNET Feature |
|--------------|--------------|-------------------|
| Financial reports | Mode φ+ | Femtosecond timestamps + XRPL witnessing |
| Document editing | Mode φ | Phase-rotation encryption |
| API calls (general) | Mode 1 | Post-quantum encryption, constant-time ops |
| Legacy system compat | Mode 0 | AES-256 with ternary key schedule |
| AI report queries | Configurable | Per-query security mode selection |

### Integration Points

1. **Kong Plugins** — enforce encryption/compression/timestamping at the gateway
2. **AI Report Service** — security mode parameter on every query, XRPL witnessing for Mode φ
3. **Document Operations** — phase-rotation encryption on WOPI traffic
4. **Audit Trail** — femtosecond timestamps on critical operations, timing certificates

### Current Status

PlenumNET integration is **framework-ready** — the type system, interfaces, and placeholder hooks are in place. Actual implementation depends on:

- HPTP protocol client (Task 4.1)
- Kong custom plugin development (Task 4.2)
- PlenumNET security middleware (Task 3.2)

```typescript
// SSE listener invalidates TanStack Query cache
const evtSource = new EventSource('/api/events/stream');
evtSource.addEventListener('project.updated', (e) => {
  const data = JSON.parse(e.data);
  queryClient.invalidateQueries({ queryKey: ['projects', data.id] });
});
evtSource.addEventListener('document.saved', (e) => {
  const data = JSON.parse(e.data);
```
